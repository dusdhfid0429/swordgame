# 구조 점검과 최적화 (2026-10-19, v152)

사용자 요청: "게임 구조 전체 점검하고 컨텐츠간의 유기적인 프로그래스 체크 및 중복 코드 확인과 최적화 진행. 최적화의 기준은 중복 코드 제거, 중복 데이터 제거, 성능 최적화."

점검은 진행 흐름, 중복 코드·죽은 코드, 성능·중복 데이터의 세 갈래로 나눠 했다. 아래 표에서 **고침**은 이번에 바꾼 것이고, **제안**은 게임 설계가 바뀌거나 위험이 커서 결정을 기다리는 것이다.

## 3. 성능

측정: 헤드리스 크로미움(소프트웨어 그리기), 390×844 @2x, 몹 22. 한 프레임 그리기는 몹·건물·이펙트를 벡터로 매번 그리는 데 대부분이 든다. 게임 계산(update)은 1ms 안쪽이라 문제가 아니다.

| 바꾼 것 | 효과 |
|---|---|
| HUD는 값이 바뀐 것만 DOM에 쓴다 (`txt`/`sty`/`qc`/`tip`), 터치 HUD도 | HUD+레이아웃 1.9ms → 0.3ms (매 프레임) |
| 화면 가장자리 어둡게(비네트)는 크기가 바뀔 때만 그린다 | 매 프레임 전체 화면 방사형 그라디언트를 없앰 |
| 매 틱 `mobs`·`fx`·`texts`·`drops`를 새 배열로 거르던 것을 제자리에서 거른다 (`prune`), 먼지 효과용 배열 펼치기 없앰 | GC 줄임 |
| `isDark` 색 판정을 색마다 한 번만 | 이펙트마다 매 프레임 하던 문자열 쪼개기 없앰 |

해 보고 되돌린 것: 밤 불빛을 그라디언트 대신 미리 그린 그림으로 찍기. 소프트웨어 그리기에서는 오히려 밤 프레임이 10ms쯤 느려져 되돌렸다.

다음 단계로 큰 효과가 날 곳 (제안):
- 몹 그리기가 프레임의 절반쯤: 팔레트별 그라디언트 캐시, 멀리·많을 때 간단히 그리기, 자세별 그림 캐시
- 건물을 그림으로 캐시 (개봉 건물 6채에 18ms쯤)
- 계절·노을·폭염 전체 화면 덧칠이 겹치면 하나로
- 모바일 메모리: 피격 흰빛용 아틀라스 복사본이 37MB쯤, 의복 색 바꾸기가 단계마다 34MB쯤. `HERO2` 가로 16,410px는 휴대폰 텍스처 한계(16,384)를 넘는다 → 줄로 나누기

## 4. 중복 데이터와 파일 크기

`dist/gangho.html` 2.8MB 가운데 그림(base64)이 65%, 코드 28%, 데이터 4.6%. 같은 그림이나 데이터가 두 번 들어간 곳은 없다.

제안:
- `HBODY`는 `HERO`와 화소 94.7%가 같다(칼집과 칼만 지운 것). 불러올 때 `HERO`에서 만들면 약 200KB(7%) 줄어든다
- `r_atlas.js`·`r_atlas2.js`의 그림을 `assets/`로 옮기고 WebP로 바꾸면 10~15% 더 준다 (`HERO2`를 나눈 뒤)
- `r_proto_arts.js`의 초식 표(9.6KB)는 밸런스 데이터라 `data/arts.json`으로
- 문파 id로 묶인 표 9개(`SECT_DATA`, `HQ_THEME`, `LOOK`, `START`, `SIM_TRAIT`, `LM_SECT`, `HALLS`, `SECT_STYLE`, `PSECT`)를 문파마다 한 덩어리로. 바이트는 2~3KB만 줄지만 문파 하나를 더할 때 고칠 곳이 9곳에서 1곳이 된다
